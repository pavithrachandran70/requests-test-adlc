## Schema/API Contracts

### Internal API Change

**Modified:** `_urllib3_request_context` in `src/requests/adapters.py`

**Signature (conceptual):**

```python
def _urllib3_request_context(
    request: PreparedRequest,
    verify: bool | str | None,
    cert: tuple | str | None,
    poolmanager: PoolManager
) -> dict:
    """
    Build urllib3 request context for connection pooling.
    
    Returns a dict with keys: 'url', 'headers', 'cert_reqs', 'ca_certs', etc.
    
    Behavioral contract:
    - If poolmanager has a custom ssl_context (non-None), omit 'cert_reqs' 
      from the returned dict to preserve the context's verify_mode.
    - If no custom ssl_context and verify=True, set 'cert_reqs' to CERT_REQUIRED.
    - If verify=False, set 'cert_reqs' to None.
    """
```

**Detection logic:**

```python
# Pseudocode for custom context detection
custom_context = getattr(poolmanager, 'connection_pool_kw', {}).get('ssl_context')
# OR
custom_context = poolmanager.connection_pool_kw.get('ssl_context') if hasattr(poolmanager, 'connection_pool_kw') else None
```

**Conditional branch:**

```python
if custom_context is not None:
    # Skip cert_reqs override; let urllib3 use context's verify_mode
    pass
elif verify is True:
    context['cert_reqs'] = resolve_cert_reqs(None)  # CERT_REQUIRED
else:
    context['cert_reqs'] = None
```

### Test Interface

**New unit tests in:** `tests/test_adapters.py`

**Test case 1: Custom SSLContext preserved**

```python
def test_custom_sslcontext_preserves_verify_mode():
    """
    AC-1: After init_poolmanager(ssl_context=ctx) where ctx.verify_mode 
    is ssl.CERT_NONE, the pool's cert_reqs does not force CERT_REQUIRED.
    """
    import ssl
    from requests.adapters import HTTPAdapter
    
    adapter = HTTPAdapter()
    ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
    ctx.check_hostname = False
    ctx.verify_mode = ssl.CERT_NONE
    
    adapter.init_poolmanager(connections=10, maxsize=10, ssl_context=ctx)
    
    # Retrieve pool key for https://example.com/
    # Assert pool's cert_reqs is NOT CERT_REQUIRED (should be None or CERT_NONE)
    pool = adapter.poolmanager.connection_from_url('https://example.com/')
    assert pool.conn_kw.get('cert_reqs') != ssl.CERT_REQUIRED
```

**Test case 2: Default verify=True enforced**

```python
def test_default_verify_enforces_cert_required():
    """
    AC-2: A request with verify=True and no custom context sets 
    cert_reqs to CERT_REQUIRED.
    """
    import ssl
    from requests.adapters import HTTPAdapter
    
    adapter = HTTPAdapter()
    adapter.init_poolmanager(connections=10, maxsize=10)
    
    # Retrieve pool key for https://example.com/ with verify=True
    pool = adapter.poolmanager.connection_from_url('https://example.com/')
    assert pool.conn_kw.get('cert_reqs') == ssl.CERT_REQUIRED
```

**Note:** Tests must mock or inspect the pool manager's internal state without opening a real socket connection.

## Risks

### R-1: urllib3 version compatibility

**Impact:** The pool-key construction logic and `resolve_cert_reqs` function may vary across urllib3 versions. If the pool manager API or `cert_reqs` resolution changes, the fix may not work.

**Mitigation:** Verify the change against the urllib3 version pinned in `pyproject.toml`. Check urllib3's documentation and source for the `connection_pool_kw` attribute and `ssl_context` storage mechanism. If the API has changed, update the detection logic to match.

**Likelihood:** Low (urllib3 API is stable).  
**Severity:** High (fix will not work).  
**Status:** Open. Verify urllib3 version during LLD.

---

### R-2: Existing adapter tests break

**Impact:** The pool-key construction change may alter the pool-key format or pool-manager behavior in ways that break existing tests in `tests/test_adapters.py`.

**Mitigation:** Run `python -m pytest tests/test_adapters.py` after the change. If tests fail, investigate whether the failure is due to:
  - A genuine regression (fix the code).
  - A test assumption that needs updating (update the test).

**Likelihood:** Medium (pool-key logic is widely tested).  
**Severity:** Medium (tests must pass per AC-3).  
**Status:** Open. Run full test suite during Dev.

---

### R-3: Custom context detection is fragile

**Impact:** If the pool manager does not expose the `ssl_context` reference via `connection_pool_kw`, or if the attribute name changes, the detection logic will fail.

**Mitigation:** Inspect the urllib3 `PoolManager` source to confirm the attribute name and structure. Add defensive checks (e.g. `hasattr(poolmanager, 'connection_pool_kw')`) to avoid `AttributeError`. If the reference is not accessible, escalate to the architect for a design revision.

**Likelihood:** Low (urllib3 API is stable).  
**Severity:** High (fix will not work).  
**Status:** Open. Verify pool manager structure during LLD.

---

### R-4: Hostname check preservation unclear

**Impact:** The ticket's expected behavior mentions "hostname checks", but AC-1 and AC-2 do not test them. If hostname checks are controlled by the `ssl_context` (via `check_hostname`), the fix may inadvertently break hostname verification.

**Mitigation:** Clarify during LLD whether hostname checks are controlled by the pool-key construction or by the `ssl_context`. If the pool-key construction sets `assert_hostname`, ensure it is not overridden when a custom context is present. Add a test case if needed.

**Likelihood:** Medium (hostname checks are a related concern).  
**Severity:** Medium (may require additional test coverage).  
**Status:** Open. Clarify during LLD or tests step.
